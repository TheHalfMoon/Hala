## Commercial license obligations

Apache-2.0 allows commercial use/modification/redistribution with license copy, modification notices, applicable copyright/patent/trademark attribution and NOTICE, and patent conditions. It does not grant trademark rights. MIT requires retention of copyright and permission notices. Some checkpoint roots contain only explicit official license declarations, not the full text. Preserve those pinned declarations and standard license text; do not invent a missing file. Qwen3-VL source Apache license was separately captured at [`96588727e44c78b25ba03ea03b8e12f7e64fd0da`](https://github.com/QwenLM/Qwen3-VL/tree/96588727e44c78b25ba03ea03b8e12f7e64fd0da). This source license corroborates the model card, but is not itself a replacement weight license declaration.

The two Liquid licenses are **not Apache-2.0**. Exact text defines "Commercial Use" as direct/indirect commercial advantage or compensation and "Threshold" as annual revenue of $10,000,000 or more. Sections 5(a-b) condition commercial rights on not exceeding the threshold and say entities exceeding it are not licensed. The definition and operative wording leave a boundary interpretation issue: do not assume $10M exact-boundary eligibility. "Legal Entity" aggregates controlled/common-control entities, not merely product revenue. Nonprofit exception applies only to non-commercial/research purposes. Redistribution sections 4(a-d) require license copy, notices on modified files, retained applicable notices and NOTICE attribution. Derivatives remain subject to commercial conditions; separable/linking works are excluded from the derivative definition, not exempted from use conditions. Founder revenue/entity eligibility and redistribution packaging remain unresolved. Compare an independently trained small classifier under a permissive license.

## Processor, formats and runtime risks

Qwen3-VL and these Qwen3.5/Holo processors declare `Qwen3VLProcessor`, `Qwen2VLImageProcessorFast`, patch 16, temporal patch 2 and merge 2. Preprocessor pixel bounds are large library configuration limits, not a sensible production screenshot budget. Preserve original screenshot dimensions, processor resizing/crops and coordinate transforms. Evaluate RGB JPEG/PNG/PIL decode, aspect ratio, small controls and RTL using the exact processor and model pin. ShowUI declares Qwen2VLProcessor with patch 14 and outputs relative coordinates in `[0,1]`; its navigation dictionaries contain `action`, `value`, `position`. Use strict JSON schemas, never `eval` or ad-hoc code execution.

Qwen3-VL card originally recommended Transformers 4.57.0 (config `4.57.0.dev0`). PyPI 4.57.6 existence was checked for a pinned baseline candidate, but import/inference are not tested. Use explicit FP16 and SDPA for old T4/P100 hardware after actual capability checks; do not assume BF16/flash-attn support. Holo3.1/Holo4 configs were authored with 5.6.2; Qwen3.5's config version string is stale relative to its newer architecture and is not a verified minimum. Its card recommends source builds of serving engines. Exact version/runtime qualification must precede downloading remote weights.

Liquid d1 is a typed decision API. `system_one(state, questions, images=None, audio=None)` returns named `noul` probabilities, `choice` selections/distributions or ordinal `score`; output_tokens is zero because answers come from distributions. Omni supports one media mode per request, PIL image(s) or a <=30-second 16 kHz mono clip; image-associated text is truncated to 896 tokens and total context is 16,384. Its card requires Transformers >=5.15 and `trust_remote_code=True`; CPU float32/GPU float16 are recommended, and BF16 is discouraged by vendor calibration checks. d1-3B requires >=5.14, custom decision code and 32,768 context. Review exact pinned remote code and dependencies rather than enabling remote code blindly. Arabic tags do not prove Arabic routing accuracy; Omni audio training is English.

No model may mint authority, override cancellation, authorize commands, assert task success or fabricate receipts. d1's vendor scores are decision benchmark evidence only. The user already observed severe local decision misses; local advisory output cannot satisfy independent security/release gates.

## Training, quantization and unknowns

Start with a no-training pinned baseline. Then a small remote LoRA SFT experiment may test owned synthetic GUI/plan pairs against held-out templates; target modules, image token budget, optimizer memory and exact runtime need measurement. Do not assume all attention/linear-state models share a LoRA recipe. Full fine-tuning optimizer states and activations can greatly exceed weights. For quantization, compare FP16 with 8/4-bit variants using identical held-out tasks and report grounding regressions/calibration before any serving choice. Holo family announces FP8/NVFP4/GGUF variants, mostly 35B first; no compact quantized variant was independently evaluated here.

Registry weight-only ideal lower bounds are `total_parameters * {2,1,0.5}` bytes for FP16/INT8/INT4. They exclude scales, unquantized modules, activations, state/KV cache and runtime overhead. Real GPU requirements, residency, warm/cold latency, Arabic/RTL competence, wrong-target rate, complete-task success and verified-task cost remain **unknown**. Vendor benchmarks have different harnesses, step limits, datasets and costs; they do not rank foundations on Aladdin workflows.
