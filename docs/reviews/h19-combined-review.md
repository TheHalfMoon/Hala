## Must-fix

- **P2 — `development/simulator.py:77-80,92-95`: observing before a failure bypasses the required recovery observation.** `observe()` sets `observed=True` unconditionally; the first transient failure does not reset it. Reproduction: select a transient-failure episode, call `sim.observe()` before editing, perform correct type/drag/save, then immediately save again without observing the failure. Actual result: success=true, action_errors=0, recoveries=1, environment_errors=1. The claimed requirement is that the first save failure requires observing that failure before retrying; a prior ordinary observation cannot satisfy it. Reset the observation/recovery flag when creating a new transient failure, or tie observation to the current failure generation/status. Add a negative test proving pre-failure observation cannot authorize the post-failure retry and a positive test proving a subsequent observation enables recovery. Preserve environment-error versus model-error distinction.

## Worth considering before model comparison

- **`development/runner.py:47`: closed-loop scores do not measure Mind plan/subgoal correctness.** The runner uses only the first tool from a plan, accepts `next` when initially asked for a plan, and discards every subgoal and remaining plan. An intentionally wrong Mind callback that always returns `visual/save_changes` for edits/drags and `observe/verify_save` for failures, including wrong initial `next` kind, completes with success=true/model_errors=0/action_errors=0. The separate ten Mind decision cases *do* exact-score semantic correctness, so task success itself is valid as the declared tool-routing/full-goal-Type architecture. Add explicit per-call Mind requested-kind/semantic accuracy metrics or clearly report this as tool-selection-only closed-loop Mind evidence. Do not describe task success as validating decomposition or subgoal correctness. Do not inject oracle subgoals into the Type prompt as a shortcut.
- **Training usefulness remains narrow, as mostly disclosed.** All eight application families share one edit/drag/save state machine and operation order; train/test names, requested strings and layouts differ. This is genuine family-key separation and novel held-out text/layout context, but weak evidence of application/task generalization. Reliance training has only `mind` (16), `clarify` (2), `abstain` (2); it provides no positive `deterministic`, `type` or `observe` routes. Mind training has no `next/visual/replace_field` completion (first steps are always a complete plan), despite the standalone held-out visual case expecting that answer. These are disclosed-small-data design limitations rather than provenance leakage. Add targeted authored examples in a later prospective data revision if those capabilities are to be claimed or trained usefully.
- **Freeze settings are caller-owned.** The source accepts any nonempty settings dictionary, including just `{"seed":42}`; a completed freeze alone does not prove model revision, precision, prompt/generation policy, timeout or telemetry were specified. The later real-runtime wrapper should supply and validate an exact settings schema before pre-inference archival and bind every run to that manifest. This source phase correctly does not claim those model runs occurred.
