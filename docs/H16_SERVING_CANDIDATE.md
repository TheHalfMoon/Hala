# H16 v2 image serving candidate

Implemented experimental source; CPU contract tests use a fake engine and provide no model-quality or GPU qualification. The real v1 backend remains unavailable and v1 mock metadata remains strict. Production readiness is never enabled by the candidate path or caller flags.

`POST /v2/hala/action` accepts exactly `schema: hala.image_request.v2`, `policy_request` (the existing strict v1 request used only as a pure policy record), and `media`. Media requires bounded PNG base64, SHA-256, request/tenant/task/device/session IDs, `frame_id` equal to observation generation, `origin: [0,0]`, and `dpi: 96`. Only identity image scaling is supported; dimensions must match the PNG, and images are limited to 524288 bytes and 1048576 pixels. Existing transport body limits may impose a smaller bound; raising them is explicit server configuration. Redaction regions must contain black pixels. Media digests bind bytes to the submitted observation, not to a trusted capture device; future Aladdin integration must supply authenticated fresh observations.

The engine receives one RGB image and the goal; the remote prompt does not include observed IDs or private bounds. The independent v2 protocol `h16-v2-normalized-point-v1` accepts only `{"point":[x,y]}` with integer axes in 0..1000, either bare JSON or exactly one `json` code fence. No prose extraction, duplicate fields, extra fields or guessed protocol are accepted. The server maps each coordinate by `min(size-1, coordinate*size//1000)`, identifies exactly one eligible observed target, rejects protected or ambiguous overlapping hits, and reuses deterministic action policy validation. Confidence is `null`: model confidence is uncalibrated and is not requested or invented. Output `hala.click_proposal.v2` carries all bindings, media digest and engine/model/processor/prompt/precision provenance. It is unqualified advice with `execution_authorized: false` and `verification_required: true`; it contains no success receipt. `/v2/hala/plan` and `/v2/hala/decision` fail closed. Authentication, admission leases, framing, deadline, disconnect cancellation and output limits reuse the existing transport. `/ready` remains the existing v1 backend readiness and does not claim v2 qualification.

`CandidateBackend()` is unavailable by default. A server-owned injected engine enables experimental candidate calls only. CPU tests label provenance `cpu_fake`. `RemoteQwenEngine.load(cache_dir)` is an optional remote-only Linux Colab loader requiring explicit `HALA_REMOTE_SERVING_ALLOWED=1` and an actual `COLAB_RELEASE_TAG` marker. It rejects the Kaggle runtime marker and an unknown `/kaggle` runtime, local Windows, and caches outside `/content` or the approved `/tmp/hala-serving-model-cache` before importing ML packages. Kaggle commercial-use eligibility remains blocked. Provider markers are diagnostics, not an adversarial proof or permission to spend. It pins Qwen/Qwen3-VL-2B-Instruct revision `89644892e4d85e24eaac8bacfd4f463576704203`, Torch 2.11.0 and Transformers 5.16.1, FP16, eager attention and `trust_remote_code=False`. It uses a 4096-token input ceiling, deterministic bounded 96-token generation and context stopping, with one active shared model call. Deadline cannot preempt an in-progress CUDA kernel; admission stays retained until the worker finishes.

No loader execution, downloaded weights, GPU E2E, release qualification, native Aladdin integration, training, public tunnel or deployment is included in CPU evidence. Actual free-session GPU serving evidence and independent Jev/PStack/Graft/CI gates remain required. Do not install these ML packages or call the loader on the personal PC.
